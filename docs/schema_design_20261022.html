0. 结论摘要

✅ 需求 ② 的字段其实已经存在，不用新增

exercises_library.exercise_type 线上已有真实数据：weight_reps 6522 条 / duration 1058 条 / distance_duration 61 条。你举的两个例子标注都是对的 （平板支撑 = duration，引体向上 = weight_reps）。

真正缺的是 ① exercises 表没有时长字段（秒数没地方存，现在被硬塞进 reps）， ② 前端 UI 完全没按这个字段分支，③ 字段名叫 exercise_type 但语义是"计量方式"，且默认值 'Strength' 是错的历史遗留（库里 0 行是这个值）。

ℹ️ 需求 ① 的动机需要修正：长度不是瓶颈，ID 粒度才是

users.practiced_exercises 在 10/22 迁移时已扩到 varchar(1000)，线上最长一条 253 字符 / 53 个 id，还剩 4 倍余量。后端也已有 CSV_MAX_LEN=950 前置拦截。

但实测挖出 4 个更严重的问题，其中两个直接影响功能正确性（详见 §2.1）。所以建表这件事该做， 但不能只建一张 "practiced 表"，否则半年后还要再迁移一次。

🚨 共同前置项：动作库有严重重复，会直接毁掉这两个功能

exercises_library 7641 行里，993 组英文名重复（多出 1287 行冗余，占 17%）， 702 组中文名重复。"Push-up" 13 行、"Crunch" 13 行、"引体向上" 11 行、"平板支撑" 2 行完全重复 （id 1914 / 1916，连 name 都一模一样）。

🔴 第 6 处错误（初版数据造假）："72 个悬空 id" 是我的 SQL 写错

初版 §2.1 断言"users.practiced_exercises 里有 72 个 id 在 exercises_library 中不存在"，并据此推断"库里的动作被删过"。

2026-11-04 两种独立方法交叉验证，结论是 0：

方法A (JS Set 逐段精确比对)          → 悬空 0 个, 共 46 段全部命中
方法B (SQL 正确段提取 + NOT EXISTS)      → 悬空 0 个
exercises 表引用但 library 没有的孤儿 id → 0 个
library id 分布: 1~9 / 10~99 / 100~451 / 1452~5880 / 27100~48277
                 → 天然稀疏(多批追加导入),不是删除留下的洞

根因：我原来那条 SQL 用 SUBSTRING_INDEX(SUBSTRING_INDEX(CONCAT(str,','), n, 1), ',', -1) 取第 n 段， 实际取到的是第 (n-1) 段（因为 SUBSTRING_INDEX 的 n 表示"第 n 个分隔符之前"）。 偏移一位导致取值错乱，产生 72 个假阳性。

结论：动作库没有被删除过的动作 —— 这条数据风险不存在， "悬空 id 清洗"这一步整个删掉。

✅ 第 7 处修正（最重要）：名字重复不是问题,是我的过度设计

用户原话:"动作库名字重复又如何呢?id唯一不就可以了么" —— 质疑成立。

我初版给关联表加了 canonical_id 列,理由是"用户练了 101 个 id 但实际只练过 92 个动作, 标记会不亮"。实测证明这个理由站不住:

"Lever Chest Press" 3 个 id (204/205/3516) 共 93 条训练记录:
    204 → 57 条 / 15 场    205 → 20 条 / 5 场    3516 → 16 条 / 4 场
  → 分布在 24 场不同的 session 里, 是"24 场训练分别选了 3 个条目",
    不是"一次训练被切碎"。用户在变体之间切换, 只亮选过的那个 = 正确行为。

整个库 212 场训练里, 同一 session 内出现同名多 id 的只有 4 场 (1.9%),
且那 4 场用户可能是真要练两个变体。

993 组同名条目: 图片全为空的 0 组, 视频全为 NULL 的 0 组, 954 组各有多个不同图片
  → 每条都是独立的、有自己资源的动作条目。

结论:同名不同 id 是合法数据(不同握法/角度/器械的变体)。 强行归组反而会误标 —— 用户练了 3 个变体,不该把 13 个全标成"练过"。

连带收益:去掉这层间接后,后端返回给前端的 id 集合就是原始 id, 前端 8 处 includes(id) 零改动,语义直通。 我初版说的"前端改动量 ≈ 0"本来就不成立,现在反而真的成立了。

名字重复真正留下的问题（与关联表无关,单独处理）

  1. 列表可读性 —— 702 组中文名重复(11 个"引体向上",英文名分别是 Chin-ups / Pull up / Chin-Up / Muscle-up…)。数据上每个 id 都有独立图片, 用户能靠图区分,但只显示中文名时看着重复 → UI 层补英文名副标题,不动数据
  2. 翻译错位 —— id=2081 name_zh='引体向上' 但 name='Mountain Climber'; id=2077 name_zh='混合握距引体向上' 但 name='Middle Back Stretch'。 中文名是后加的,中间错位 → 人工核对 name_zh ↔ name 对应关系

这两项都不要用"归组"解决 —— 归组会误标,还会掩盖真实的数据问题。

补充修正:duration 动作不一定不需要 weight

初版写"duration 类隐藏 weight"。但实测 27 条 duration 记录里 24 条 weight>0, 样本 "1 2 棒训练" = reps=10, weight=40lb —— 这是负重动作, 被错标成 duration。

  `user_id`      int NOT NULL,

  `update_time`  timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

3.5 卡路里算法 v1（独立文件）

为什么独立成文件

原来卡路里散在两处,而且是同一个公式抄了两遍:

前端 utils/unit.js:        volumeToCalories(volume)  ← 同一公式

用户拍板:"要计算,先单开一个卡路里计算的算法文件,先写一套简单的算法, 后续再根据动作类型的不同进行优化"

duration MET × weightKg × durationSec / 3600 MET 默认 5(中等强度)
distance_duration weightKg × distanceKm × 0.9 距离法(跑步经验公式), 距离必填 → 更准
