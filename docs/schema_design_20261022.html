0. 结论摘要

✅ 需求 ② 的字段其实已经存在，不用新增

exercises_library.exercise_type 线上已有真实数据：weight_reps 6522 条 / duration 1058 条 / distance_duration 61 条。你举的两个例子标注都是对的 （平板支撑 = duration，引体向上 = weight_reps）。

真正缺的是 ① exercises 表没有时长字段（秒数没地方存，现在被硬塞进 reps）， ② 前端 UI 完全没按这个字段分支，③ 字段名叫 exercise_type 但语义是"计量方式"，且默认值 'Strength' 是错的历史遗留（库里 0 行是这个值）。

ℹ️ 需求 ① 的动机需要修正：长度不是瓶颈，ID 粒度才是

users.practiced_exercises 在 10/22 迁移时已扩到 varchar(1000)，线上最长一条 253 字符 / 53 个 id，还剩 4 倍余量。后端也已有 CSV_MAX_LEN=950 前置拦截。

但实测挖出 4 个更严重的问题，其中两个直接影响功能正确性（详见 §2.1）。所以建表这件事该做， 但不能只建一张 "practiced 表"，否则半年后还要再迁移一次。

🚨 共同前置项：动作库有严重重复，会直接毁掉这两个功能

exercises_library 7641 行里，993 组英文名重复（多出 1287 行冗余，占 17%）， 702 组中文名重复。"Push-up" 13 行、"Crunch" 13 行、"引体向上" 11 行、"平板支撑" 2 行完全重复 （id 1914 / 1916，连 name 都一模一样）。

后果：用户练了 id=228「Pull up」，UI 上另外 10 个「引体向上」都不会带 ☑ 标记； 关联表建得再对，粒度也是错的。详见 §4。

2. 需求 ①：用户 × 动作 关联表

2.1 现状诊断：4 个真问题

#问题证据严重度
1 悬空 ID：库里动作被删/改 id 后，用户的"练过"标记变成指向不存在行的垃圾，永远洗不掉 users.practiced_exercises 里有 72 个 id 在 exercises_library 中不存在 高
2 ID 粒度错：动作库有重复行，"练过"标记只命中用户实际练过的那一个 id 993 组英文名重复 / 多 1287 行；"引体向上" 11 行 高
3 筛选靠前端回传：library.list 把整个 id 数组拉到客户端再传回来做 IN (...)，既可篡改也需 MAX_FILTER_IDS=500 钳制 library.service.ts:57-72 中
4 只有布尔位：答不了"练过几次""多久没练""历史最佳重量"，以后加统计还得再 ALTER + 回填 现表仅 favor_exercises / practiced_exercises 两列 中

附带修掉一个老 bug

exercises_library.is_favorite 是全局共享列 —— 任意登录用户调 toggleLibraryFavorite 会让全体用户的收藏标记同步翻转（已记录在 code_quality_plan_20261013.md P2-5）。 关联表的 is_favor 是 per-user 的，顺手根治。

2.2 表设计（推荐）

CREATE TABLE `user_exercise_stats` (
  `user_id`           int NOT NULL,
  `exercise_id`       int NOT NULL,
  `is_favor`          tinyint NOT NULL DEFAULT 0 COMMENT '是否收藏',
  `is_practiced`      tinyint NOT NULL DEFAULT 0 COMMENT '是否练过(至少一次)',
  `practice_count`    int NOT NULL DEFAULT 0 COMMENT '累计训练次数',
  `last_practiced_at` timestamp NULL DEFAULT NULL COMMENT '最近一次训练时间',
  `best_weight`       float DEFAULT NULL COMMENT '历史最佳重量(统一 kg 存储)',
  `best_reps`         int DEFAULT NULL COMMENT '最佳成绩次数',
  `create_time`       timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`       timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`user_id`, `exercise_id`),
  KEY `idx_ues_exercise` (`exercise_id`),
  KEY `idx_ues_user_practiced` (`user_id`, `is_practiced`, `last_practiced_at`),
  CONSTRAINT `fk_ues_user` FOREIGN KEY (`user_id`) REFERENCES `users`(`id`) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

字段设计逐条理由

设计决策理由
PK = (user_id, exercise_id)
不用自增 id + UNIQUE		 天然幂等，同一 (user, exercise) 只有一行 → INSERT ... ON DUPLICATE KEY UPDATE 一次搞定加收藏 / 标记练过；删用户自动 CASCADE
is_favor 与 is_practiced 合并一张表 两者粒度完全相同（都是 user × exercise），拆两张表纯属自找 JOIN；且"练过但没收藏 / 收藏但没练过"是高频组合，合并后一次查询拿全
practice_count + last_practiced_at 支撑"练过几次""多久没练了""最近练的哪些"；更重要的是一次建到位，只存布尔位的话以后加统计还得 ALTER + 回填一遍
best_weight 统一存 kg 现在 exercises 是 weight + weight_unit 双列，聚合要做 CASE WHEN；关系表直接存归一化值，统计直接 MAX()。只在新表归一，原表不动（历史数据零影响）
idx_ues_user_practiced 支撑"最近练过的动作"列表 —— 这是 last_practiced_at 存在的意义
不设全局 is_favorite 根治 §2.1 提到的收藏全局共享 bug

语义保持：is_practiced 仍是布尔

"☑ 练过"筛选语义完全不变，布尔位保证这一点；practice_count 是纯增量信息， 不影响任何现有 UI。不改变现有语义，迁移风险最低。

2.3 迁移路径（3 步，每步可独立回滚）

1

建表 + 回填（不动任何现有逻辑）

写一次性脚本 scripts/migrate_user_flags.ts：读 users 表 → 用后端现成的 splitCsvIds() 拆 CSV → 批量 INSERT IGNORE。

⚠️ 拆 CSV 拆到"第 n 个逗号段"用纯 SQL 很绕且易错（本次实测里一条多段聚合 SQL 就踩了语法坑）。 应用层拆分更可控 —— 迁移文档 db_migration_20261013.sql STEP 7 也是这么建议的。

顺手清洗 72 个悬空 id：不在 exercises_library 里的直接跳过，不进新表 （也意味着这 72 个标记会随之消失 —— 需要你确认是否可接受）。

2

后端切读（双写保底）

  • exercises.service.ts 的 toggleCsvFlag → upsertUserExerciseFlag （INSERT ... ON DUPLICATE KEY UPDATE），顺便弃用 CSV_MAX_LEN 硬拦截
  • auth.service.ts 登录返回的 favor_exercises / practiced_exercises 格式完全不变（还是 id 数组），只是数据源从 users 列换成新表
  • library.list 的 isFavor / isPracticed 筛选改成 后端自己 JOIN 新表，不再依赖前端回传 id 数组 → 干掉 MAX_FILTER_IDS 钳制 + 篡改风险
  • 旧列保留并同步双写 1~2 个版本，作为回滚保险
3

停双写 + 删旧列

确认稳定后 DROP users.favor_exercises / users.practiced_exercises， 以及全局 bug 源 exercises_library.is_favorite。

前端改动量 ≈ 0

登录返回字段名和格式不变 → add-exercise-modal / library 的 is_favorite / is_practiced 标记逻辑一行都不用改。 唯一的净变化是 library.list 的筛选参数从"传 id 数组"变成"传布尔"，反而更干净。

3. 需求 ②：次数 / 计时 双模式

字段已存在，但名字和默认值要修

exercises_library.exercise_type 已有 weight_reps / duration / distance_duration 三个值，数据基本标对了。不需要新增字段， 但要做两件事：改个自解释的名字、修掉误导性的默认值。

3.1 Schema 改动

-- ① 重命名 + 收敛取值 + 修默认值
ALTER TABLE `exercises_library`
  CHANGE COLUMN `exercise_type` `count_mode` varchar(16) NOT NULL DEFAULT 'weight_reps'
    COMMENT '计量方式: weight_reps=重量+次数 | duration=计时 | distance_duration=距离+时长';

-- ② 补上真正缺失的采集字段
ALTER TABLE `exercises`
  ADD COLUMN `duration_sec` int   DEFAULT NULL COMMENT '计时动作持续秒数',
  ADD COLUMN `distance_m`  float DEFAULT NULL COMMENT '距离动作米数';
决策理由
改名 exercise_type → count_mode "type" 会被理解成"训练类型（力量/有氧）"，与"按次数还是按时间"是两回事。count_mode 自解释，且能通过 CHANGE COLUMN 原地改，前端只需改字段名
默认值 'Strength' → 'weight_reps' 库里 0 行是 'Strength'，纯历史遗留。默认值与实际取值域不一致会持续误导后来人
不新增第 4 个取值 现有 3 个已覆盖"次 / 秒 / 距离+秒"。真需要"只计距离"时再加，且 distance_duration 配 distance_m=NULL 已能表达
exercises 加 duration_sec，不复用 reps ① 语义污染：reps=60 是 60 次还是 60 秒？reps 参与大量 SUM/MAX(reps) 统计 SQL，改语义会让历史统计全错；② 分开存才能按 count_mode 明确回填
两个新字段都 DEFAULT NULL NULL = 不适用，0 = 适用但值为 0，语义明确不混淆；也避免给 1746 行历史数据批量写 0

⚠️ 历史数据回填：必须人工核对，不能无脑跑

那 27 条 duration 记录的 reps 值是 1~10，不是真实秒数（可能是"1 组"的意思，也可能是随手填的）。 如果直接 SET duration_sec = reps，等于把垃圾固化成"秒"。

建议做法：先人工核对这 27 条（数据量很小，10 分钟能看完），确认哪些是真秒数再回填。 其余保持 NULL，加载时按 count_mode 决定读哪个字段，duration_sec 为空则用 reps 兜底。

4. 前置阻塞项：动作库去重 + 标注错位

4.1 重复行（阻塞需求 ①）

指标实测
英文名重复组数993 组，多出 1,287 行冗余（占 7,641 行的 17%）
中文名重复组数702 组，多出 971 行
最严重"Push-up" 13 行、"Crunch" 13 行、"引体向上" 11 行、"Lever Chest Press" 8 行
完全相同（name 一字不差）平板支撑 id 1914 / 1916，name 均为 "Front Plank"

为什么这会毁掉需求 ①

用户练了 id=228「Pull up」
  → 关联表写入 (user=1, exercise=228)
  → library 列表里另外 10 个「引体向上」(112/229/339/1704/2081/2102/2103/2764/3617/4830/5870/5871)
     仍然不带 ☑ 标记
  → 用户视角："我明明练过引体向上，为什么标记没全亮？"

需求 ① 建了关联表之后，这个问题会变得更明显（因为筛选逻辑正式上线了），而不是被解决。

4.2 标注错位（阻塞需求 ②）

exercise_type 是按英文源数据标注的，中文名是后加的，中间错了位：

idname_zhname（英文）count_mode判断
2081引体向上Mountain Climberduration错 中文名被安到了登山跑上
2077混合握距引体向上Middle Back Stretchduration侥幸 拉伸确实是 duration
112/228/229/339/1704/2102/2103/2764/3617/4830/5870/5871引体向上Chin-ups / Pull up / …weight_reps对

好在你举的例子恰好没踩到

平板支撑 (1914/1916) 和绝大多数引体向上 id 都标对了，所以功能一上线你大概率看不出问题。 但 id=2081 这类错位行会让"引体向上"出现两套行为（一个按次数、一个按计时）， 用户能感知到但很难归因。建议上线前跑一遍 name_zh × name 语义不符的行做人工核对。

4.3 去重策略建议

不建议物理删除重复行 —— exercises 表里有 1,746 行历史记录引用着这些 id， 删了会断链（虽然实测 orphans = 0，但那是"引用了仍存在的行"，删除会制造新的孤儿）。

推荐：加 canonical 映射，不动原始行

ALTER TABLE `exercises_library`
  ADD COLUMN `canonical_id` int DEFAULT NULL COMMENT '归一后的动作 id, 指向代表行';

-- 代表行 canonical_id = 自己的 id；重复行 canonical_id = 代表行 id
-- 查重:  SELECT name, MIN(id) FROM exercises_library GROUP BY name HAVING COUNT(*)>1

配合需求 ①：关联表的 exercise_id 存 canonical_id， UI 展示时按 canonical 去重。这样"练过"标记自然覆盖所有重复行， 且历史数据零风险（只多一个字段 + 一次 UPDATE）。

6. 待确认问题

  1. 72 个悬空 practiced id：库里的动作已经不存在了。迁移时直接丢弃（标记消失）还是保留在旧 CSV 列里？
  2. duration 动作的 27 条历史记录：reps 值到底是不是秒数？需要你人工看一眼再决定回填策略。
  3. 计时器交互：是"手动输入秒数"就够，还是要"点开始 → 计时 → 停止自动填入"的真计时器？后者要多做一个组件。
  4. distance_duration 的 61 条：距离要用什么单位（m / km）？配速要不要算出来并进统计？
  5. 去重力度：13 行同名的 "Push-up"，是完全合并成一条，还是保留变体（如不同器械/不同角度）？后者需要你先定"什么算不同变体"的规则。
  6. count_mode 改名：要不要同时给"真正的训练类型"（力量/有氧/柔韧）留一个独立字段？现在这两件事挤在一个字段的历史包袱里。
