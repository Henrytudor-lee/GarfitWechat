最严重的一条 · 静默损坏训练数据

exercise.update 会把没传的字段写成 NULL。 后端无条件把 duration_sec / distance_km 拼进 SET 子句,没传的 push(null)。 改个重量就能把已有的秒数抹掉,改个秒数就能把公里数抹掉 —— 而且前端注释里写的"不会误清已有值"和后端实现正好相反。

第二条 · 主流程从未通过

动作库选动作 → 训练页加入,这条链路从来没通。 写端写的是上一页的 data,读端读的是 globalData,两条通道从未对接。 更糟的是:即使接上,原实现直接落库 weight:0, reps:0,而首页显示过滤是 weight>0||reps>0||duration>0||distance>0 → 所有类型的动作加进去都不显示(不只是计时/距离类)。

第三条 · 时间正确性靠运气

Node 进程时区从未被约束。 mysql2 默认 timezone='local'(按 Node 进程所在主机的时区解析 DATETIME), 而线上 MySQL 是 UTC+8。两边不一致时全部时间字段整体偏移 8 小时 —— 训练页计时器算出负数、连续打卡错、月度统计错、日历圆点错位。

B3
"连续训练天数"两个接口算法不一致 —— 同指标显示不同数字
src/modules/users/users.service.ts · src/modules/stats/stats.service.ts · ★src/common/utils/streak.util.ts
症状
users 版用 new Date().toISOString().slice(0,10)(UTC 日期)对比 mysql2 的本地午夜 → 差 8 小时 → 昨天练过时 users 返回 0、stats 返回 1。回溯窗口也不同(30 天 vs 60 天)
修法

验证

这里踩到一个真坑

第一版 SQL 写成 SELECT DATE_FORMAT(DATE(start_time), ...) ... GROUP BY DATE(start_time), 线上 MySQL 开了 only_full_group_by → 直接 1055 报错, profile.getProfile 和 stats.summary 会全挂。 是验证脚本在生产库上跑出来的,改成 MIN(DATE(start_time)) 后解决。这是本轮最惊险的一处。

10.1 严重 · W11: 计时类动作显示成四段 —— WXML 条件配对写错

根因不是设计问题, 是 wx:else 配对错了
  <view class="set-field" wx:if="{{item.countMode === 'duration'}}">        ← 时长
  <view class="set-field" wx:if="{{item.countMode === 'distance_duration'}}"> ← 距离
  <block wx:else>                                                          ← 重量 + 单位 + 次数

WXML 的 wx:else 配对的是紧邻的上一个 if/elif —— 也就是 distance 那个, 不是 duration。 于是 duration 模式下「距离 if 为 false → 走 else」→ 重量/单位/次数被一起渲染, 计时类动作显示成四段(用户截图)。

同一个文件里 add-exercise-modal 的结构是对的, 但它的 JS 又把重量强制写成 0 (weight: (isDuration || isDistance) ? 0 : weight) → 负重被直接丢弃。两个弹框既不一致, 也都表达不了负重。

10.2 三种模式的字段分配(新口径)

模式主计量重量次数时长距离
weight_reps次数✅ 重量✅ 次数——
duration时长✅ 负重—✅ 时长—
distance_duration距离✅ 负重—可选✅ 距离
为什么重量对三类都成立

计时/距离类动作也可能是负重的 —— 手握两个哑铃的交叉跳跃、负重爬坡步行、背负装备的登山。 所以对这三类, 重量不是「次数类专属字段」, 而是「这个 set 额外承受的负重」, 0 = 自重。

配套改动: add 弹框重量区不再对计时/距离类隐藏、提交不再强制置 0、标签改「负重/LOAD」并加提示; edit 弹框 buildSets 补 isDuration/isDistance/isRepsMode 标记、条件改成互斥的 wx:if; 「LAST」badge 对计时/距离类也显示(内容按模式不同, 点它回填上次的秒数/公里数和负重); 展示层三处(首页/会话详情/训练总结)让计时/距离类显示出负重, 如「45秒 · 10kg」; i18n 新增 LOAD/LOAD_HINT。

10.3 卡路里 v2 · 负重要参与计算(等效体重法)

用户拍板: 参与计算, 用等效体重法。

等效体重 = 用户体重(kg) + 额外负重(kg) × loadFactor

duration           kcal = MET × 等效体重 × 时长(小时)
distance_duration  kcal = 等效体重 × 距离(km) × 0.9
weight_reps        kcal = 训练量 × 体重 × 0.0011    ← 不动
loadFactor = 0.5 是经验系数, 不是文献定值

公开文献里没有公认的「哑铃负重 → 等效体重」折算比例。0.5 的含义: 举起哑铃时大约一半的外部负荷 真正转化为代谢负担, 其余是举起动作的机械功和动量传递损耗。文件头已写明, 后续做按动作类型的 MET 表时 这一档应该被按具体负重强度替换掉。

历史数据不变性(已实测): 2026-11-07 之前计时/距离类的 weight 被前端强制写成 0 → 负重恒为 0 → 等效体重 = 用户体重 → 旧记录算出来和现在完全一样。caloriecheck.js 新增了这条不变性检查(3 条样本全部一致)。

生产端到端实测(600 秒): 不负重 50 kcal / 负重 10kg 54.1667 kcal / 合计 104 ✅ 与手算一致。 已固化为 scripts/verify-load-calories.js。

10.4 严重 · W12: 「push 了但线上跑的还是旧代码」

排查负重 e2e 时发现的部署可靠性问题, 与算法本身无关。 症状: cf3327e 推送后 /health 的 build 字段变成新 SHA(看着像部署成功), 但负重 e2e 算出来是 100(旧算法)而不是 104。

1SHA 判据本身不可靠
/health 的 build 读的是 .git/HEAD —— 只反映 git 仓库状态, 不反映实际运行的程序。 部署是 reset → npm ci → build → pm2 restart, 任何一步失败(set -e)都会中止, 但 .git/HEAD 在中止前就更新了 → 光看 SHA 会误判成「已部署」。
2连着 push 会并发部署
一个在 npm ci(删 node_modules 重装), 另一个同时在 npm run build → 编译中途 node_modules 被抽走 → build 失败 → 线上跑的还是旧 dist。
层改动

workflow加 concurrency 组, cancel-in-progress: false → 不打断进行中的部署, 新 push 排队等前一个跑完, 部署永不并发。timeout 10→15 分钟
deploy.shbuild 之后比对 dist 的版本常量与源码, 不一致就中止(不让编译不完整的 dist 被 pm2 加载); pm2 restart 之后比对 /health 的 calorieAlgo, 对不上就中止并打 pm2 日志(旧进程照样能返回 /health 200, 只看 200 不够)
测试验证脚本一律用专用测试账号, 不用 users 表第一个(id=1 正好是用户自己的账号)

  <text wx:if="{{s.duration_sec > 0 && s.weight > 0}}">·</text>
  <text wx:if="{{s.duration_sec > 0 && s.weight > 0}}">负重</text>
  <text wx:elif="{{s.distance_km > 0}}">距离</text>   ← elif 配对的是**上一个 if**(负重那个)
  <text wx:if="{{s.distance_km > 0 && s.weight > 0}}">·</text>
  <text wx:if="{{s.distance_km > 0 && s.weight > 0}}">负重</text>
  <block wx:else>重量 × 次数</block>             ← else 配对的是**最后一个 if>
WXML 的配对规则

wx:elif 配对紧邻的上一个 wx:if, wx:else 配对最后那个 wx:if。 于是 duration 形态下: 时长分支成立 → 紧邻的 if(负重)也成立 → elif 不生效; 而 else 配对的最后那个 if(distance 条件)为 false → else 照样渲染 → "20kg × 0 reps"。

修法: 三个分支改成相邻的 block + if/elif/else(和 pages/index 已验证正确的写法一致): workout-summary-modal 与 session-detail-modal 两处都改了(pages/index 本来就是对的)。
