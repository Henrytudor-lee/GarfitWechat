GFIT 缺失演示视频 · Lyfta 抓取实测报告

第二版（结论已修正）· 评估日期 2026-11-08 · 评估对象 my.lyfta.app / lyfta.app / apilyfta.com
⚠️ 本报告修正了第一版的两个错误结论

第一版（同名 .html 已被本文件取代）断言「这 2018 条动作在 GymVisual 源头就没有视频」。这个结论是错的。 根因是数据源选错了 —— 不是 Lyfta 没有视频，而是我用来判断的公开接口字段是过时的。

  1. 公开 POST /api/search 的 video_file 字段是旧的快照。 用它判断，id=5443 / id=1560 都返回 null； 但登录态 /api/v2/exercises/by-ids 返回的 videoFile 非空，且 URL 实测 200 可下载。
  2. 我第一版的「2000 个组号 S3 全量穷举 0 命中」是方法缺陷，不是事实。 我只试了 {组号}1201.mp4 一种 key 形式；而 Lyfta 后来补做的视频只有带描述名的路径 （如 42351201-Dumbbell-...Shoulders-.mp4），短名路径仍然是 403。

修正后的结论：Lyfta 上确实有这批动作的视频，只是公开接口不暴露。 已用登录态接口实测并落地 3 行（15 条被训练过的缺视频动作中命中 2 条，加上 1 条同组变体）。

最终成果：全量 2015 条扫描完毕，288 条视频补进生产库，坏引用清零

缺视频动作数 2018 → 1728；有视频 4968 → 5258；生产机 mp4 4727 → 5015；孤儿记录 0。

全部 2015 个 id 一次性扫完（26 批 × 80），命中 299 条 → 双校验通过 288 条（286 个 mp4 文件，2 个文件被 2 条库记录共用）， 公网可达 286/286，sha256 与生产机磁盘逐字节一致。

额外成果：全库「库引用了但磁盘上没这个文件」的坏引用从 1 条（存量）降到 0 条。

一、关键方法：登录态 API 才是准确数据源

从 Lyfta 官方 App 的 JS chunk（my.lyfta.app/_next/static/immutable/chunks/*.js，SvelteKit）里挖出了真实端点与参数：

端点认证说明
GET /api/v2/exercises/by-ids?ids=1,2,3session cookie 批量按 id 取，一次最多 200 个。这是本报告唯一使用的数据源
GET /api/v2/exercises/search?search=&limit=&offset=session cookie 按名字模糊搜（参数名是 search，不是 query）
POST https://lyfta.app/api/search免鉴权 公开可用，但 video_file 字段过时 → 不可信
GET https://lyfta.app/exercise/{slug}免鉴权 页面 __NEXT_DATA__ 里的 video_file 同样过时
GET /api/v1/exercises/libraryAPI Key 需 Authorization header，登录 cookie 不行

登录态返回的关键字段（比公开接口多）： 

{
  "id": "5443",
  "name": "Dumbbell Seated Bent Over Rear Delt Row",
  "gymVisualId": "4235",
  "imageName": "https://apilyfta.com/static/GymvisualPNG/42351101-Dumbbell-..._small.png",
  "videoFile": "https://apilyfta.com/static/GymvisualMP4/42351201-Dumbbell-..._Shoulders-.mp4",
  "videoName": null,
  "dateModified": "2025-09-30T14:18:23.000Z"
}

关联安全性的关键发现：组号 100% 一致

gymVisualId 就是 GymVisual 的 4 位组号（4235 → 图片名 42351101-…）。 凡是有 videoFile 的记录，其 mp4 的组号与它自己图片名的组号完全相同（抽样 60 条中命中的 11 条，11/11 一致）。 也就是说 补视频不存在「张冠李戴」风险 —— 拿到的就是同一个动作的演示视频，不是变体。 这与之前「同名 ≠ 同动作」的教训不冲突：那次是按名字匹配，这次是按素材组号匹配。

自动校验规则（抓脏数据的关键）

批量补库前对每条候选做双重校验，两个条件都必须过：

  1. 编号严格比对：视频文件名的 8 位编号必须严格等于「库内 image_name 前 4 位 + 1201」。
  2. 名称 token 重合度：视频文件名主干与库内英文名的有效 token 重合度 ≥ 0.34（剔除 male/female/version 等变体词与器材词后计算）。

实测抓到 Lyfta 侧的错配脏数据，而且量不小：id=279「Lever Side Hip Abduction」的 videoFile 是 103421201-Reverse-Hyperextension-on-Box_Hips_.mp4 —— 编号是 1034+21201（多了个 2）， 文件名主干指向<完全另一个动作>「Reverse Hyperextension on Box」。仅靠组号校验会放过它，靠名称校验才抓出来，已剔除。
第 5 批里同类脏数据密集出现（10 条，编号形如 100031201、101261201）， 说明Lyfta 这批 2025-09 补做的视频数据本身就带错配。 结论：组号一致是必要条件，不是充分条件 —— 双校验缺一不可。

素材复用：一个 mp4 可补多条库记录

53 个 mp4 文件覆盖了 55 条库记录 —— 01641201-Cable-Front-Shoulder-Raise_Shoulders_.mp4 同时对应 id=66 与 id=1615， 01721201-Cable-Incline-Pushdown_Back_.mp4 同时对应 id=71 与 id=1623（GFIT 库与 Lyfta 库一样存在同素材多 id 复用）。 批量补库按文件去重后上传，避免重复下载。

执行链路

  1. 从 apilyfta.com 下载 mp4（ftyp 文件头校验通过，大小与 Content-Length 一致）
  2. 先验公网可达（200 video/mp4）再写库 —— 不让库指向坏文件
  3. 写库前备份 3 行 → .gfit-backup-video3-1794118590692.json
  4. 走 PUT /admin/library/:id 更新（自动写 admin_operation_log 审计）
  5. scp 推生产机 /media/gfit/exer_videos/，文件名为原始 GymVisual 名
  6. 公网 https://gfit.l2ee.top/exer_videos/{name} 验证 + sha256 与本地完全一致

关于文件名：一个走弯路的决定

第一次用 admin 上传接口（POST /admin/upload），它会把文件名净化成 42351201-Dumbbell-Seated-Bent-Over-Rear-Delt-Row_Shoulders.mp4（去掉尾部 -）。 但生产机现有 4727 个 mp4 里 2828 个是原始 GymVisual 名（带括号、尾部 -）。 功能上没问题（资产匹配只取前 4 位组号，两种命名都能命中），但两套命名混在一个目录里不干净。 已改为直传原始名，并把净化版移到生产机 ~/.trash-gfit/（不 rm，可恢复）。

批量补库踩到的三个坑（已修正，写进流程）

  1. Lyfta 的 videoFile 字段本身有截断 bug —— 少数条目（如 id=2798）数据库里存的文件名被截成 14461201-Barbell-Zercher-Squat-Hold-Isometrics_.mp4，真实名是下划线版 …-Hold_Isometrics_.mp4，CDN 上前者 404、后者 200。 处理：下载失败时按 imageName 描述反推后缀变体（试 15-25 种）找回真名；找不回就回滚成无视频，绝不留 404 链接。
  2. 下载校验失败 ≠ 可以跳过写库 —— 我第一版脚本里「文件非 mp4 → 跳过上传」但写库环节没跟着跳过， 导致 2 行库指向不存在的文件。铁律：先验 URL 200 → 下载 → ftyp 校验 → 已上传 → 才允许写库， 四步缺一不可。
  3. 名称 token 重合度会误伤 —— id=2838「Sledge Hammer」对文件名 Sledgehammer-Slam， 分词后重合度 0，但编号 14961201 完全匹配、显然是同一动作。 处理：重合度只作「标记」不作「否决」，编号严格匹配才是硬条件。

四、剩余 1728 条的最终定性

全部 2015 条已扫完：命中 299 条（14.8%），双校验通过 288 条，11 条因 Lyfta 数据错配被剔除。 剩余 1728 条经全量核验确认：Lyfta 侧确实没有视频（videoFile 为 null）， 且对应组号在 GymVisual CDN 上确认不存在（403 / 404）——这部分不是抓取能力的问题，是源头没有素材。 这批全部从未被用户训练过（训练明细 2100 条里没有一条引用它们），对用户体验影响最小。

五、遗留的技术事实（省得以后重查）

  • Lyfta 是 SvelteKit 应用，chunk 在 /_next/static/immutable/chunks/*.js， 路由表在 /_next/static/{buildId}/_buildManifest.js。
  • GymVisual CDN 有两套 key 形式：早期视频有短名 {组号}1201.mp4（S3 桶 lyftaweb.s3.us-east-2.amazonaws.com）， 后来补做的只有带描述名的（apilyfta.com/static/GymvisualMP4/{组号}1201-{描述}.mp4）。 只查一种形式会漏判 —— 这是我第一版翻车的地方。
  • S3 桶不能 ListBucket（AccessDenied），只能逐个 GET；403 = key 不存在（用假组号 9999/0000/8888 对照验证过）。
  • gymvisual.com 整站 403（按 UA/来源拦截），但 apilyfta.com 与 S3 可直连。
  • GFIT 库 id = Lyfta by-ids 的 id（已验证 id=2 / 45 / 1560 / 5443 等一致）。 但 不要把 gymVisualId 当 id 传 —— 我第一次这么干，导致返回的全是别的动作。
  • 本机 Downloads 里那 9 个 GymVisual mp4 早就全部上传并写库了（历史遗留，零漏网）。
  • 本机 Chrome 历史里可查到你之前的抓取痕迹：my.lyfta.app/exercises、Google 登录流程、 以及 lyftaweb.s3.../GymvisualMP4/06521201.mp4（Pull-up，组 0652，已在库）。

六、本轮我自己犯的三个错误（已修正，记录在案）

  1. 数据源选错：用公开 /api/search 的 video_file 判断「有没有视频」，而该字段是过时快照。 → 修正：改用登录态 /api/v2/exercises/by-ids。
  2. 穷举方法缺陷：S3 全量探测只试了纯编号 key 一种形式，漏掉了只有带描述名路径的新补视频。 → 修正：以登录态 API 返回的完整 URL 为准，不再猜 key 形式。
  3. 传参错误：批量查询时把 gymVisualId 当成 id 传，导致返回的全是别的动作，一度让我以为 id 体系对不上。 → 修正：传 GFIT 库 id，并用 GFIT 库逐条对账。
验证方法说明：全部结论来自生产库只读查询、生产机磁盘实测、Lyfta 登录态 API 实测、CDN HTTP 状态码与 sha256 实测。 对照实验用于排除三类误判：①公开接口字段过时 ②S3 key 形式单一 ③S3 403 是否等于「不存在」。 本轮唯一的生产库写操作是 3 行 video_name 更新（已备份、已审计、已 sha256 校验）； 其余全部为只读扫描，未从 Lyfta 下载除上述 2 个 mp4 之外的任何素材。
