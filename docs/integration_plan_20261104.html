2. 数据库改动总表（精确到列）

2.1 改动一：exercises 表加 2 列

-- scripts: docs/db_migration_20261026_phase1.sql
ALTER TABLE `exercises`
  ADD COLUMN `duration_sec` int   DEFAULT NULL COMMENT '计时动作持续秒数'  AFTER `reps`,
  ADD COLUMN `distance_km` float  DEFAULT NULL COMMENT '距离动作公里数 (km)'  AFTER `duration_sec`;
列类型为什么
duration_sec int NULL 计时动作(平板支撑/波比跳)的秒数。NULL = 该动作不适用, 0 = 适用但值为 0 —— 语义明确, 避免给历史数据批量写 0
distance_km float NULL 距离动作(跑步/骑行/划船)的公里数。字段名带单位 —— 单位绑进字段名后, 以后改单位得 ALTER + 数据换算, 一次定死

2.2 改动二：新建 user_exercise_stats 表

-- scripts: docs/db_migration_20261104_phase3.sql
CREATE TABLE IF NOT EXISTS `user_exercise_stats` (
  `user_id`      int NOT NULL,
  `exercise_id`  int NOT NULL COMMENT '动作 id (exercises_library.id), 不做归组',
  `is_favor`     tinyint NOT NULL DEFAULT 0 COMMENT '是否收藏',
  `is_practiced` tinyint NOT NULL DEFAULT 0 COMMENT '是否练过(至少一次)',
  `create_time`  timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`  timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`user_id`, `exercise_id`),
  KEY `idx_ues_exercise` (`exercise_id`),
  CONSTRAINT `fk_ues_user` FOREIGN KEY (`user_id`) REFERENCES `users`(`id`) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
设计理由
PK = (user_id, exercise_id) 天然幂等 → ON DUPLICATE KEY UPDATE 一次搞定 toggle;删用户自动 CASCADE
is_favor + is_practiced 合并一张表 两者粒度完全相同(user × exercise),拆两张纯属自找 JOIN
不做任何归组(无 canonical_id) 同名不同 id 是合法的独立条目(不同握法/角度/器械的变体), 每条都有独立图片视频。用户练了 3 个变体就该只亮 3 个,归组反而是误标
不存派生统计列 "练过几次""最佳重量"全都能从 exercises 明细实时聚合。 冗余存一份 = 双份事实来源 + 同步问题

3. 需求①：用户 × 动作 关联表

为什么值得做

线上 users.practiced_exercises 是逗号串, varchar(1000), 上限约 190 个 id。当前最长一条 253 字符 / 43 个 id,离上限还有 4 倍余量 —— 所以长度不是紧急问题,但结构问题是真的:

  • 并发读-改-写整串会丢收藏(已用行锁 + FIND_IN_SET 修过,但仍是整串操作)
  • 旧 CSV 写满了会静默截断 / ER_DATA_TOO_LONG
  • 无法支撑"练过几次""多久没练"这类后续需求

★ 关键设计:数据决定行为,不用配置开关

新增 UserExerciseFlagsService,启动后探测一次新表是否存在:

状态读写
新表不存在(迁移前)旧 CSV 列旧 CSV 列 行为和现在完全一致,零影响
新表存在(迁移后)关联表关联表 + 旧列双写 旧列是回滚保险
要回滚DROP 掉新表 → 自动退回旧逻辑,不用改代码不用重启

所以代码可以在 Phase 3 迁移之前就部署,不用卡发布顺序。

前端零改动

登录返回的 favor_exercises / practiced_exercises 字段名和格式完全不变 (还是 id 数组),前端 8 处 includes(id) 一行都不用改。

library.list 的收藏/练过筛选也不用改 —— 前端传的 id 数组本来就是登录时 从后端拿的同一份数据,后端内部切读路径它自动就对了。

⚠️ 这里刻意没有改成后端自取:现有代码注释里写明, 前端对收藏是乐观更新(先本地改状态再 fire-and-forget 提交), 改成服务端自取会出现"刚收藏完立刻点筛选 → 筛出空列表"的 UX 回归。

5. 卡路里算法 v1

为什么独立成文件

原来是同一个公式抄了两遍,而且整个 session 一个公式,不区分动作类型:

后端 sessions.service.ts:  Math.round(totalVolume * userWeight * 0.0011)
前端 utils/unit.js:        volumeToCalories(volume)   ← 同一公式

结果:计时类(平板支撑)和距离类(跑步)的卡路里恒为 0。

v1 三档公式

count_mode公式说明
weight_repsvolumeKg × weightKg × 0.0011 沿用现有公式,不动 → 历史数据完全不变
durationMET × weightKg × durationSec / 3600 MET 默认 5(中等强度)
distance_durationweightKg × distanceKm × 0.9 距离法(跑步经验公式),距离必填 → 更准
// 后端: gfit-backend/src/common/utils/calories.ts
// 前端: fitness_wechat/miniprogram/utils/calories.js   ← 两份必须同步

export const CALORIE_CONFIG = {
  volumeFactor: 0.0011,
  defaultMet: { weight_reps: 6, duration: 5, distance_duration: 8 },
  distanceFactor: 0.9,
};
// 后续按动作类型优化时, 只改这张表, 调用方一行都不用动

⚠️ 踩到的坑:卡路里不能 JOIN exercises 聚合

-- ❌ 一个 session JOIN 出 N 行 exercise, s.calories 被放大 N 倍
SELECT COUNT(*), SUM(s.calories) FROM sessions s LEFT JOIN exercises e ON ...

-- ✅ 卡路里是 session 级的事实, 独立聚合
SELECT SUM(calories) FROM sessions WHERE _openid=? AND status='finished';

同理,前端所有"从体积反推卡路里"的地方都改成了用后端聚合的真实值 —— 新算法下 session 的卡路里不再等于 volumeToCalories(totalVolume)。

v1 已知局限（后续优化方向）

  • MET 是统一默认值 —— 平板支撑实际约 3.5 MET、波比跳约 8~10,一律按 5 → 波比跳低估一半
  • 距离法系数统一 0.9 —— 跑步 0.9 / 骑行 0.75 / 划船 1.0
  • 距离法优先于时长 —— 填 5km + 10 分钟(实际没跑完)会高估
  • 肌肉分布图漏掉计时/距离动作 —— 它按体积分摊,那些动作 volume=0

优化入口都收敛在 CALORIE_CONFIG 和 metOverride 参数上 —— 按动作查 MET 表时由调用方传入 metOverride 即可,公式本身不用改。

典型: 卧推 60kg×10 → 39.6 / 平板支撑 60秒 → 5 / 跑步 5km → 270

实跑抓到的 2 个真 bug（肉眼看 SQL 发现不了）

  1. CSV 段提取 off-by-one —— 补逗号后第 n 段要用 SUBSTRING_INDEX(..., n+1); 写成 n 的话多段 CSV 丢最后一段、单段 CSV 整条丢失(实测丢了 user1 的 '2052'、user2 的 '27819'、user4 的 '3715')
  2. CAST('' AS UNSIGNED) 严格模式抛错 —— n=1 取到空串, Truncated incorrect INTEGER value: '' → 整个 INSERT 失败。 修法:NULLIF(..., '')
