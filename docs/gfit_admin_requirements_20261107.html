核心判断

现有后端无任何动作库写接口，但基础设施（MySQL 连接、媒体存储、文件白名单、部署流水线）齐全。后台管理是增量开发而非重建，路径清晰。

但生产 3000 端口公网裸奔且无鉴权——若按常规方式把 admin 部署上去，会直接造出一个无鉴权的公网写接口。用户选择的「不用登录，仅本机本地运行」恰好是正确方向，需要落实为技术约束。

项目结论
建议形态独立前端仓库 gfit-admin（Vue3 + Element Plus），后端在 gfit-backend 新增 admin 模块
建议鉴权admin 服务不部署到生产，本机运行 + 共享密钥 + loopback 限定（§4.2）
建议首版范围动作库 CRUD + 素材上传 + 用户/动作数据只读查看（用户原话三块）
可复用资产TypingService 批量改 type 引擎、MysqlService、LocalStorageService 路径防护、部署流水线、49 项安全回归测试

03 关键设计决策

3.1

硬删除的级联语义

实测外键现状 —— 两个引用方向都没有外键保护：

exercises.exercise_id          → exercises_library.id   ❌ 无外键
user_exercise_stats.exercise_id → exercises_library.id  ❌ 无外键
（两表只对 session_id / user_id 有 FK）

无外键 = 删库行不会自动清引用，会产生孤儿记录（当前孤儿数 0，是项目一直维护的不变量）。后台删除必须显式在一个事务里做三件事：

START TRANSACTION;
DELETE FROM exercises            WHERE exercise_id = ?;  -- 训练明细
DELETE FROM user_exercise_stats  WHERE exercise_id = ?;  -- 收藏/练过标记
DELETE FROM exercises_library    WHERE id = ?;           -- 库行本体
COMMIT;

删除前必须提示影响面：当前被训练记录引用的动作共 107 个，Top1（Bench Press, id=2）牵涉 142 条训练记录。删除弹窗必须显示「将同时删除 N 条训练记录 / 影响 M 个用户」并二次确认。

建议删除动作时不删物理文件。同一张图片可能被多个 id 复用（生产上 6853 个引用对 6852 个文件），物理文件先留着，后续用独立「素材体检」功能统一清理孤儿文件更安全。

3.2

新增动作的 id 分配

方案做法评价
A改表加 AUTO_INCREMENT⚠️ 会重排 id 语义，改动风险中等
B应用层取 MAX(id)+1（事务内 FOR UPDATE）✅ 推荐 —— 零 schema 改动，后台单人操作锁竞争可忽略
C加 seq_id AUTO_INCREMENT 代理键改动大，前端全部逻辑用 id，收益低

推荐 B，并在应用层强制 id 唯一性校验。

3.3

字典体系 —— 发现一个现存缺口

equipment_id / body_part_id 是逗号分隔的多值字符串，字典散落在前端硬编码：

  • 小程序 pages/library/index.js 硬编码 28 个器械 + 16 个肌群
  • 后端 typing-rules.ts 只有 BODY_PART_LABEL（20 项），没有 equipment 标签表
维度库里实际用到的值前端字典覆盖
equipment_id1–28 全覆盖，另有 19 条是多值（如 "4,23"）28 项全覆盖
body_part_id1–21（21 个值）只有 16 项，缺 11/13/14/15/16/21

缺口影响：库里有 945 个动作（body_part 命中 11/13/14/15/16/21）用到了前端没有的部位 id —— 这些动作在小程序里无法被部位筛选命中，用户按「爆发/功能」「杠铃力量」「瑜伽姿势」筛选时结果是空的。后台上线后应能把这类值可视化并批量校正。

3.4

多值字段的筛选语义不一致

body_part_id 用 FIND_IN_SET 匹配（后端已这么做，正确）。但 equipment_id 后端用的是精确匹配 equipment_id = ? —— 对那 19 条多值记录（"4,23"）永远匹配不到。

后台管理列表应统一用 FIND_IN_SET 语义，与小程序筛选行为对齐。

3.5

素材命名策略

现有文件名形如 00251101-Barbell-Bench-Press_Chest-FIX_small.png，编码来源不明（00251101 疑似「素材序号+部位码+器械码」）。后台新建动作时：

  • 选项 1：完全沿用旧编码规则 —— 规则不明，需逆向推导
  • 选项 2（推荐）：新规则 {slug}_{timestamp}.{ext}，只要求唯一 + 可读，不与旧规则混用

旧规则已有 2 条因括号截断损坏，新规则能避免同类问题。

04 安全评估（本次评估重点）

高危

生产 3000 端口公网裸奔

$ ss -tlnp
LISTEN 0 511 0.0.0.0:3000  users:(("node /opt/gfit-..."))
$ iptables -L INPUT
Chain INPUT (policy ACCEPT)     ← 无任何过滤规则

$ curl http://47.108.200.98:3000/health
{"status":"ok","service":"gfit-backend",...}    ← 从外网直接命中

Nginx 虽然配了 /api 反代，但 3000 端口本身对外可达，绕过了 Nginx 的所有 location 配置。

这对后台管理是致命的：如果把 admin 模块按常规方式部署到生产，它会立即成为无鉴权的公网写接口 —— 任何人都能改动作库、删训练记录。

用户已选择「不用登录，仅本机本地运行」，这恰好是正确方向，但需要落实为技术约束。

鉴权方案落地（三层防护）

层措施效果
L1 网络admin 服务不部署到生产，本机运行（npm run start:dev + ADMIN_ENABLED=true）生产上根本没有 admin 路由可打
L2 传输本机 → 生产库的写入走 SSH 隧道 + 只读账号；写操作单独走一个受限通道数据库层面不暴露写权限
L3 应用admin 路由双重校验：① 请求必须带仅存在于本机环境变量的共享密钥 ② 拒绝任何非 loopback 来源即使密钥泄露，从公网也打不进来

额外必做：修复 3000 端口暴露 —— 生产 main.ts 改为 app.listen(port, '127.0.0.1')，让 Nginx 成为唯一入口。这一条独立于后台项目，但属同一批安全债，改动极小、收益极高。

中危

library.typingApply 无角色校验

// rpc.controller.ts:86-91 —— 普通用户的 JWT 就能调用
case 'library':
  if (sub.startsWith('typing')) {
    return this.typing.handle(sub, openid, data);  // openid 只用于数据隔离
  }

typingApply 能批量修改全库 7641 个动作的 exercise_type，却走的是普通用户鉴权路径 —— 任何登录用户理论上都能调。

建议：把 typingSuggestions / typingApply 从 /api RPC 通道下线，只保留在 admin 模块下。这同时也是用户需求「批量修正动作类型」的一部分。

中危

upload 的 ownerHash 机制与动作库素材冲突

现有上传强制 objectName 形如 {prefix}/{ownerHash}/{ts}-{rand}.{ext}，用于归属校验（防删他人头像）。但动作库素材是全局共享的裸文件名（exer_images/xxx.png），两套约定不兼容。

admin 上传需单独实现：前缀白名单改为 exer_images / exer_videos；不带 ownerHash（全局资源无归属概念）；删除动作不删物理文件。

现有防护可直接继承

  • FileTypeValidator 魔术字节白名单（防存储型 XSS）
  • LocalStorageService 路径穿越防护
  • AllExceptionsFilter 生产环境错误泛化
  • 分页参数钳制（防拉爆内存）

05 架构方案

选型（已确认）

gfit-admin/                    独立前端仓库 · Vue3 + Vite + Element Plus
   ├─ views/
   │   ├─ library/     动作库列表 · 详情 · 编辑器
   │   ├─ upload/      素材上传（拖拽 · 进度 · 预览）
   │   ├─ users/       用户列表 · 用户详情
   │   └─ analytics/   动作使用分析 · 数据质量体检
   ├─ api/            admin.* 路由封装
   └─ vite.config.ts  dev 代理 → http://127.0.0.1:3000

gfit-backend/                加一个 admin 模块
   src/modules/admin/
   ├─ admin.controller.ts      REST 风格路由（不走 /api RPC 兼容层）
   ├─ admin.service.ts         动作库 CRUD · 批量操作 · 事务
   ├─ admin-upload.service.ts  动作库素材上传（exer_images / exer_videos）
   ├─ admin-metrics.service.ts 用户/动作只读统计
   └─ admin-auth.guard.ts      §4.2 的 L3 校验

为什么 admin 不走 /api RPC 兼容层

现有 /api 是给小程序 RPC 兼容用的，鉴权模型是「微信 openid + JWT」。后台管理的鉴权模型完全不同（共享密钥 + loopback 限定 + 操作审计）。

混在一个入口里会让鉴权分支越来越难审计 —— 这正是历史上 toggleLibraryFavorite 越权和 typingApply 无角色校验的成因。独立 /admin/* 前缀 + 独立 Guard，能让「谁能改数据」这个问题一眼可查。

写操作审计

用户已选「不用登录」，但改生产库的动作必须有审计。建议建 admin_operation_log：

id, ts, op, target_table, target_ids, affected_rows, payload_snapshot, client_ip

后台每次写操作记一行。理由很直接：37 个真实用户的数据，且历史上已有过「误写生产库 20 行」的记录。

06 待确认事项

  • 1. 新建动作的素材文件名规则沿用旧编码 / 新规则 {slug}_{ts}.{ext}　→　建议新规则（旧编码规则不明且已损坏过）
  • 2. 后台是否需要「合并同名动作」需要 / 不需要　→　建议需要。993 组同名是最大的长期数据债，合并 = 改引用 + 删一行，正是后台该做的事
  • 3. 删除动作时是否保留媒体文件保留 / 一并删除　→　建议保留，孤儿文件用独立「素材体检」功能清理
  • 4. 是否同期修复 3000 端口暴露修 / 不修　→　建议修，改动 1 行，独立于本项目但同批安全债
  • 5. 是否同期下线 typingApply 的 RPC 暴露下线 / 保留　→　建议下线，迁移到 admin 模块
  • 6. 后台第一个可用版本的范围仅动作库 CRUD / 全量　→　建议动作库 CRUD + 素材上传 + 用户/动作只读查看（用户原话三块）
